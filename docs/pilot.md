# 首轮用户试点

状态：计划，尚未招募或取得付费结果。本页用于安排试点，不作为产品已被市场验证的依据。

## 要回答的问题

缺少测试设备的开发者，能否借助执行包和第三方测试者，得到足以复现问题的反馈？重复测试时，准备和复核所需的人力是否比现有方式更低？

首轮计划邀请五位主要使用 Mac、但需要发布 Windows 应用的开发者。Windows 有现成样本验证记录，适合作为第一轮范围；macOS / Linux 需取得目标系统执行证据后再扩大试点。

## 输入与安排

参与者提供近期的真实 EXE、MSI 或 ZIP，以及 3–5 个关键步骤。优先标准控件、单窗口工具；驱动、重启、复杂提权和登录流程单独评估。

应用方提供构建与预期，测试者提供专用、可还原的 Windows 环境。双方明确可执行时间、费用、证据范围和留存期限，按[执行策略](execution-strategy.md)交付。

## 对照方法

在相同初始环境，分别记录人工验收与 Prooflane 的准备、执行和整理反馈时间。自动化首次配置成本单独计入；不要只比较配置完成后的运行时间。

每个构建建议重复三次，重置环境并交替执行顺序。请开发者判断是否能凭报告复现问题，再记录修复后是否实际需要复测。

| 记录项 | 方法 |
| --- | --- |
| 构建与环境 | 匿名任务编号、SHA-256、系统和架构 |
| 人工基线 | 准备、操作、整理反馈分别计时 |
| 自动化成本 | 首次配置、每次执行、人工介入分别计时 |
| 问题分类 | 区分应用问题、自动化误报和环境失败 |
| 反馈质量 | 开发者能否复现，还缺少什么信息 |
| 使用意愿 | 是否实际提交下一个构建，是否实际付费 |

成本包含机器占用、人工处理、存储和传输。意向报价和实际支付分别记录。

## 结束后判断

以下是待验证的内部门槛，不是现有数据：至少四位完成一个真实流程；重复运行结果一致率达到 90%；配置后的人工介入比基线减少一半；至少两位购买下一次测试。

门槛未达到时先看具体原因：控件定位失败则收窄应用范围并改进诊断；配置时间过长则检查是否需要有人协助；没有复测需求则暂不扩大设备投入。
